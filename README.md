# ДНК-метр — стенд калибровки/поверки датчиков

Программно-аппаратный стенд для калибровки датчиков ДНК-25 / ДНК-М: задаёт
ток возбуждения через датчик (замкнутый контур на источнике питания + одном
мультиметре), ждёт стабилизации, читает выходной сигнал датчика вторым,
независимым мультиметром, пишет результат в CSV.

Это не просто код — это ещё и подробный отчёт о боевом вводе стенда в
эксплуатацию: что сломалось, как чинили, что осталось открытым. Написано,
чтобы можно было продолжить отладку с нуля на другом ПК, не гоняя всё то же
самое по кругу.

## Быстрый старт

```bash
conda create -n dnkmetr python=3.11
conda activate dnkmetr
pip install -r dnkmetr/requirements.txt
```

Дополнительно на реальном стенде нужен **NI-VISA** (`visa32.dll`) —
[ni.com/en/support/downloads/drivers/download.ni-visa.html](https://www.ni.com/en/support/downloads/drivers/download.ni-visa.html).
Без него `pyvisa.ResourceManager()` не найдёт ни один прибор.

```bash
cd dnkmetr
python main.py                      # mode: fake из config.yaml — без железа
python main.py --config config.yaml # то же самое явно
```

Чтобы работать с реальными приборами — поменять `mode: fake` на `mode: real`
в `config.yaml` (см. раздел «Архитектура» ниже, что для этого нужно проверить
заранее).

## Архитектура

```
main.py           — точка входа, грузит config.yaml, зовёт measure.run_session()
measure.py         — сценарий измерения: предполётная проверка цепи ОС,
                     сходимость тока, чтение выхода датчика, запись CSV
current_control.py — HardwareCCController (если у источника есть аппаратный
                     CC) и SoftwarePIController (velocity-form ПИ + бинарный
                     поиск стартовой точки) — общий интерфейс step()/is_stable()
drivers.py         — универсальный SCPI-драйвер (PowerSupply/Multimeter),
                     ничего не знает про конкретный вендор — только про роль
instruments/*.json — один файл = один прибор: SCPI-команды + параметры связи.
                     Смена прибора = новый JSON + строчка в config.yaml,
                     БЕЗ правок кода (см. instruments/README.md)
config.yaml        — какие приборы, какие профили/VISA-ресурсы, коэффициенты
                     контура, шунт, список датчиков
tune_current_loop.py — подбор Kp/Ki на модели нагрузки (FakePowerSupply),
                     без железа
```

### Схема цепи

Две независимые токовые петли, два разных мультиметра:

```
[Источник GPP-4323, CH1]──[RIGOL DM3068, режим A]──[датчик, вход возбуждения]
                                                          │
                                            (внутреннее преобразование датчика)
                                                          │
                              [АКИП B7-78/1, режим A]──[шунт ~1кОм]──[датчик, выход]
```

- **feedback_multimeter** (RIGOL) — в контуре обратной связи, опрашивается на
  каждом шаге ПИ-регулятора, держит ток возбуждения на уставке.
- **measurement_multimeter** (АКИП) — читает выходной ток датчика один раз
  после стабилизации. Датчик по входу — датчик напряжения, но **выход у него
  токовый**, поэтому АКИП стоит в режиме амперметра
  (`sensor_circuit.measurement_mode: "direct_current"` в конфиге), а не меряет
  напряжение на шунте.
- Шунт (~1 кОм) — нагрузочный резистор на выходе датчика (burden resistor),
  нужен, чтобы токовый выход датчика мог работать в штатном режиме при своём
  ограниченном compliance-напряжении. В расчёт тока программно не участвует
  (АКИП меряет ток напрямую) — валидируется отдельно, см. `validate_shunt()`
  в `measure.py` и `sensor_circuit.shunt_min_ohms`/`shunt_max_ohms` в конфиге.

## Приборы стенда

| Роль | Прибор | VISA-ресурс | Статус |
|---|---|---|---|
| power_supply | GW Instek GPP-4323 (шильдик 74323) | `ASRL4::INSTR` (COM4) | все команды профиля проверены вживую |
| feedback_multimeter | RIGOL DM3068 | `USB0::0x1AB1::0x0C94::<serial>::INSTR` | **см. открытую проблему ниже — подозрение на предохранитель** |
| measurement_multimeter | АКИП-B7-78/1 (Prist V7-78/1, на платформе PicoTest) | `USB0::0x164E::0x0DAD::<serial>::INSTR` | проверено вживую |

## Сага про GW Instek GPP-4323: от "устройство не определяется" до рабочего USB

Это был самый долгий и самый поучительный кусок работы, расписываю подробно —
пригодится, если история повторится на другом ПК/приборе.

### Симптом 1: Windows вообще не видит прибор (Код 28)

После переустановки/обновления NI-VISA источник перестал определяться в
системе. Диспетчер устройств показывал ошибку **Код 28 — "для устройства не
установлены драйверы"**, хотя раньше (по словам оператора) всё работало без
дополнительных драйверов.

**Диагностика:**

```powershell
Get-PnpDevice | Where-Object { $_.FriendlyName -match 'GPP|Instek' }
Get-PnpDeviceProperty -InstanceId <InstanceId> -KeyName DEVPKEY_Device_HardwareIds
```

Аппаратный ID устройства — `USB\VID_2184&PID_0057&REV_0254`. VID `0x2184` —
GW Instek. Класс интерфейса — `Class_FF&SubClass_01&Prot_02`, то есть
**vendor-specific**, не CDC-ACM (не "виртуальный COM-порт из коробки"). Такому
классу Windows принципиально не может подобрать драйвер сама — обязательно
нужен вендорский INF.

**Проверенный, но тупиковый путь**: в системе уже стоял драйвер WCH CH341SER
(частый USB-serial мост). Проверка его INF (`C:\Windows\INF\oem*.inf`,
искать `ch341ser.inf`) показала, что там прописаны только ID самого WCH
(`VID_1A86`, `VID_4348`), причём **все они помечены `ExcludeFromSelect`** —
то есть этот драйвер не только не подходит по VID, но и не появился бы в
списке "Обновить драйвер → Выбрать из списка уже установленных драйверов"
при попытке подсунуть его вручную. Раньше "работало без доп. драйверов",
скорее всего, означало, что нужный вендорский драйвер уже стоял в системе от
старой установки софта GW Instek, а вовсе не то, что прибору драйвер не
нужен в принципе.

**Решение**: официальный драйвер с сайта производителя —

> **GW Instek USB Driver Ver.1.0.0.3** —
> https://www.gwinstek.com/en-global/download/downloadFile/14674

(`driverSetup.exe`, Inno Setup, `CompanyName: GWInstek, Inc.`, без
цифровой подписи, но с официального домена gwinstek.com — ставился с
правами администратора):

```powershell
Start-Process -FilePath "driverSetup.exe" -ArgumentList "/VERYSILENT /SUPPRESSMSGBOXES /NORESTART" -Verb RunAs -Wait
```

ExitCode 0 → устройство переопределилось как **`GPP Serial (COM4)`**, статус
OK, VISA-ресурс `ASRL4::INSTR`. Параметры порта: **115200 8N1**.

```
*IDN? → GW INSTEK,GPP-74323,SN:GEZ823770,V1.22
```

### Симптом 2: команды доходят, но прибор не отвечает (одностороняя связь)

Отдельный эпизод, уже после того как COM-порт заработал: `*IDN?` и другие
запросы возвращали **ноль байт**, при этом `VSET1:3.21` реально выставлял
напряжение на передней панели (подтверждено визуально). То есть путь
ПК→прибор работал, а прибор→ПК — нет.

**Проверено и исключено** (через голый `pyserial`, в обход VISA):

- скорости 4800 / 9600 / 19200 / 38400 / 57600 / 115200
- терминаторы `\n`, `\r\n`, `\r`
- все 4 комбинации DTR/RTS
- `pnputil /restart-device` (сам вернул ExitCode 1, не помог)

Раз путь ПК→прибор работал (значит, скорость обмена гарантированно верна) и
USB-шина исправна в обе стороны, проблема была не в ПК/драйвере/кабеле, а в
самом приборе — скорее всего, в состоянии его прошивки/UART-моста.

**Что помогло**: полный цикл питания прибора (выключить кнопкой питания,
подождать ~10 c, включить) + возврат baud rate на 115200 + переключение на
другой порт USB-хаба. После этого `*IDN?` снова отвечает штатно.

**Важно на будущее** (из мануала GPP Series, стр. 99–103):

- Только ОДИН интерфейс дистанционного управления активен одновременно
  (RS-232/USB/GPIB/LAN) — выбирается через **System → F1 (Interface) → F2
  (USB)**.
- Название порта в статус-баре серое при выборе, белое — после первой
  успешной команды.
- **Долгое нажатие F6 (unlock) на передней панели отключает режим
  дистанционного управления** — если это случайно нажать, связь с ПК
  пропадёт до повторного выбора интерфейса.

### Баг парсинга: единицы измерения в ответе

`VOUT1?` и `IOUT1?` отвечают **с суффиксом единиц** (`"00.000V"`,
`"0.0000A"`), а не голым числом, как отдают мультиметры. Прямой `float()` на
таком ответе падает. Исправлено в `drivers.py` — добавлен `_parse_number()` /
`ScpiInstrument.query_number()`, вытаскивающий число регуляркой
(`[-+]?\d*\.?\d+(?:[eE][-+]?\d+)?`) из ответа любого формата.

### Итог по GPP-4323

Все команды профиля (`gwinstek_psu_generic.json`) подтверждены вживую:
`VSET1:`/`ISET1:` (с readback `VSET1?`/`ISET1?`), `ALLOUTON`/`ALLOUTOFF`,
`VOUT1?`/`IOUT1?`. Канал `1` захардкожен в шаблонах команд осознанно — в
tracking-series режиме (`TRACK1`, CH1=master+CH2=slave) управление идёт
только через CH1, это следствие физической проводки, а не runtime-выбор.

**Не проверено**: возвращает ли `VOUT1?` в tracking-series суммарные 0-64В
по обеим клеммам, или только напряжение CH1 — гипотеза из мануала, не
подтверждена прямым измерением.

## RIGOL DM3068: подозрение на битый предохранитель токового входа (ОТКРЫТАЯ ПРОБЛЕМА)

Это **не решено** и стоит проверить в первую очередь на новом месте.

**Симптомы по порядку:**

1. Изначально RIGOL в контуре ОС показывал `~1 нА` независимо от
   приложенного напряжения, при этом источник (через собственный, хоть и
   грубый, амперметр) видел реальную нагрузку на несколько мА. Диагноз —
   мультиметр физически вне разрыва токовой петли. Оператор переподключил
   щупы — один раз (после исправления) RIGOL честно совпал с источником
   (8.71 мА против 9.3 мА).
2. Дальше проблема вернулась в другом виде: RIGOL стабильно показывал
   **примерно 1/40–1/50 от реального тока** (не шум, а устойчивое, повторяемое
   отношение — при 4В/7В/10В отношение было ~39x/47x/50x, независимо от
   типа нагрузки — что тестовый резистор 3кОм, что магазин сопротивлений,
   что три 3кОм-резистора параллельно (~1кОм)). Переподключение щупов
   несколько раз подряд ничего не меняло — числа воспроизводились с точностью
   до третьего знака.
3. `FUNC?` на самом RIGOL честно показывает `DCI` (режим измерения тока), и
   `SYST:ERR?` — `No error`. То есть настройки прибора верны, ошибок прибор
   не сообщает — а токовый вход всё равно ведёт себя как высокоомный делитель.

**Рабочая гипотеза**: частично (не полностью) перегоревший предохранитель
токового входа (мА/A). Не до конца сгоревший предохранитель — это не
разрыв, а большое, но конечное сопротивление; вместе с реальным собственным
входным сопротивлением измерительного тракта DMM оно образует делитель тока,
что и объясняет наблюдаемую картину: пропорциональный, но заниженный в
постоянное число раз ток, воспроизводимый независимо от внешней нагрузки, и
без ошибок со стороны самого прибора (предохранитель — не часть SCPI-логики,
прибор о нём "не знает").

**Что проверить в первую очередь на новом месте:**

1. Омметром при выключенном источнике — сопротивление между входными
   клеммами RIGOL в режиме измерения тока (мА/A щупы). У исправного DMM это
   доли–единицы Ом. Килоомы — предохранитель именно такой, "полуживой".
2. При подтверждении — заменить предохранитель (номинал указан рядом с
   гнездом мА/A на передней панели) или временно посадить на роль
   `feedback_multimeter` другой мультиметр.

**Как это ловится программно**: `measure.check_feedback_path()` в
`measure.py` — подаёт пробное напряжение и сравнивает приращение показаний
самого ОС-мультиметра между 0 В и пробным напряжением (НЕ сравнивает
абсолютно с показаниями источника — то была первая версия проверки, она
давала ложные срабатывания, см. ниже). Если приращение меньше порога —
исправление цепи требуется, о запуске измерения не может быть и речи.

### Побочная находка: собственный амперметр источника (GPP-4323) грубый

Изначально `check_feedback_path()` сравнивал показания ОС-мультиметра с
собственным амперметром GPP-4323 (`IOUT1?`). Выяснилось, что этот встроенный
амперметр квантуется шагом порядка 0.1–1 мА и на токах 1–3 мА систематически
занижает (пример: RIGOL честно видел 1.56 мА при 5В на резисторе 3кОм, а
источник в этот же момент показывал 0.1–0.3 мА). Из-за этого проверка ложно
считала цепь разомкнутой. Исправлено — проверка теперь сравнивает
ОС-мультиметр САМ С СОБОЙ (0В → пробное напряжение), не полагаясь на
точность встроенного амперметра источника.

## АКИП: определение модели по VID/PID

Прибор физически подписан как "АКИП" (частый в РФ ребрендинг), но
представляется в системе как `Prist,V7-78/1,...`. USB VID `0x164E`
идентифицируется как **Picotest Corp.** — то есть это PicoTest-платформенный
B7-78/1, а не Siglent-платформенный АКИП-2101 (для него на всякий случай
тоже сделан профиль — `instruments/akip_2101.json`, **не проверен**).

`MEAS:VOLT:DC?`/`MEAS:CURR:DC?` работают одношагово, без предварительной
настройки функции/диапазона (`SENS:FUNC`+`RANG:AUTO OFF`+`READ?`, как было в
первоисточнике IVtrace_dev, здесь не потребовалось).

## Контур регулирования тока: баги, находки, тюнинг

### Баг: `dt` в формуле — константа из конфига, а не реальное время шага

`SoftwarePIController` — ПИ-регулятор в velocity-форме
(`dV = Kp*(error−prev_error) + Ki*error*dt`, без отдельного интегратора —
накопление идёт через `self._voltage`). Коэффициенты изначально подбирались
на модели нагрузки (`FakePowerSupply`, ~800 Ом, см. `tune_current_loop.py`) —
там `dt=0.2с` было честным временем шага.

На реальном железе один шаг (VISA/serial round-trip до обоих приборов)
стабильно занимает **~0.4–0.45 с**, то есть вдвое дольше настроенных
`dt=0.2с`. Код использовал константу `self.dt` в формуле интегральной
составляющей и в slew-rate лимите — регулятор "думал", что между шагами
прошло меньше времени, чем на самом деле, интегратор недокручивал вдвое
медленнее реального времени, и петля стабилизировалась на устойчивом
смещении в разы больше требуемой точности.

**Исправлено**: `_wait_tick()` теперь возвращает РЕАЛЬНОЕ прошедшее время, и
именно оно, а не `self.dt`, используется в формуле и в slew-rate лимите.

### Добавка: бинарный поиск стартового напряжения (`coarse_seed()`)

Линейный разгон через `step()` со slew-rate лимитом тратил 20–28 шагов
(9–13 c реального времени) только на то, чтобы "нащупать" примерный рабочий
диапазон напряжения. Для резистивной/квазирезистивной нагрузки
зависимость тока от напряжения монотонна — значит, можно найти нужное
напряжение бисекцией за `log2(диапазон/точность)` шагов (~13 итераций при
допуске 0.02В на диапазоне 0–60В) вместо десятков линейных приращений.

`SoftwarePIController.coarse_seed()` — бисекция по `[0, max_voltage]`,
после неё `step()`/ПИ включается уже почти без ошибки: доводит точность и
отслеживает медленный дрейф, а не тратит время на разгон.
`measure.measure_one()` вызывает `coarse_seed()` автоматически, если
контроллер его поддерживает.

**Предположение бисекции**: монотонная зависимость тока от напряжения у
рабочей точки. Для резистивной тестовой нагрузки это точно так; для
реального датчика нужно перепроверить перед использованием (датчик — не
чисто резистивный элемент).

### Результаты тестов на реальном стенде (тестовая нагрузка вместо датчика)

Тестировалось на прецизионных резисторах (3кОм, затем 3×3кОм параллельно
≈1кОм) вместо датчика — конкретное значение нагрузки для оценки самого
алгоритма не принципиально.

| Прогон | Сходимость | Удержание 10мА (60с) |
|---|---|---|
| До фикса `dt` | 28 шагов / 12.6 с | среднее 9.734 мА, std 0.041 мА, p2p **0.29 мА (2.9%)** |
| После фикса `dt` | 19 шагов / 9.0 с | среднее 9.729 мА, std 0.035 мА, p2p 0.25 мА — офсет почти не изменился |
| + бинарный поиск | 13 итераций поиска (~10.5с) + 4 шага ПИ (12.5с) | среднее 9.749 мА, std **0.011 мА**, p2p **0.062 мА (0.62%)** |

Целевая точность от пользователя: окно ±0.01мА (±0.1%, `9.99–10.01`),
приемлемый худший случай ±0.05мА (±0.5%, `9.95–10.05`). После бинарного
поиска **разброс (p2p) укладывается в худший случай** (0.062 < 0.1мА), но
пока не дотягивает до строгой цели, и среднее systематически на ~2.5% ниже
уставки — см. следующий пункт, почему.

### Побочная находка: тепловой саморазогрев тестового резистора

При удержании тока ~10мА через резистор 3кОм рассеивается ~0.31 Вт — этого
хватает на заметный дрейф сопротивления вверх при длительной работе без
охлаждения. Прямое наблюдение: на фиксированном напряжении 30.99В ток
сначала точно выходил на 10.007мА, потом медленно плыл вниз (10.0073→10.0055
мА за 14с) — верный признак роста R при нагреве. После ~20+ минут
почти непрерывных тестов на одном и том же резисторе сопротивление
"уползло" примерно вдвое (с ~3.1кОм до ~6.2кОм по независимым оценкам через
показания источника) — настолько, что напряжения 60В (потолок источника)
уже не хватало на 10мА.

**Вывод**: систематическое занижение среднего в таблице выше — это не
столько ограничение алгоритма регулирования, сколько артефакт нагрева
тестовой резистивной нагрузки при повторных прогонах без остывания. Перед
финальной оценкой точности на реальном датчике стоит либо давать нагрузке
остыть между прогонами, либо ориентироваться на **разброс (p2p/std) внутри
одного прогона**, а не на офсет среднего от уставки.

## Безопасность стенда

- `max_voltage_v: 60.0` в `current_loop` — паспортный максимум GPP-4323 в
  tracking-series 64В, поставлено с запасом. **Не поднимать выше 64В.**
- Аппаратное ограничение тока источника (`ISET1:`) — первая линия защиты,
  выставляется перед каждым включением выхода.
- Программный abort по `saturated_steps` в `SoftwarePIController` — если
  напряжение упёрлось в потолок, а ток всё ещё далёк от уставки, заезд
  обрывается вместо ожидания общего таймаута (признак обрыва цепи).
- `measure.check_feedback_path()` — предполётная проверка целостности цепи
  ОС перед каждым датчиком.
- Выход источника гарантированно гасится в `finally` во всех тестовых
  скриптах и в `measure_one()`.

## Тесты

- **Fake-режим** (`mode: fake`, без железа) — полный прогон
  `python main.py` проходит целиком, пишет CSV с обоими тестовыми
  датчиками. Регрессионный тест на каждое изменение `measure.py`/
  `current_control.py`/`drivers.py`.
- **`tune_current_loop.py`** — подбор Kp/Ki на модели нагрузки, без железа.
- Все тесты на реальном железе, описанные выше (ВАХ, предполётные проверки,
  сходимость, удержание, шумовой пол RIGOL) — one-off скрипты в процессе
  отладки, не входят в репозиторий как автотесты, но их результаты и логика
  описаны здесь и частично перенесены в `measure.check_feedback_path()` и
  `SoftwarePIController.coarse_seed()`.
